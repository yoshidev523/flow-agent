# Flow Implement

## 目的

`spec/{yyyymmdd_feature}/plan.md` をもとに、計画されたタスクを実装し、
検証結果と進捗を `spec/{yyyymmdd_feature}/implement.md` に記録する。

このスキルは、実装・テスト・検証の実行に集中する。コミット、push、PR 作成はユーザーが明示的に依頼した場合だけ行う。
implementer は plan で決まったことをプロジェクトの実装ルールに沿って順番に実行する。
plan にない設計判断が必要な場合は推測で進めず、実装前ブロックとして扱う。

## 実行主体

- このスキルの実装、検証、進捗記録、追加作業、フィードバック反映は、必ず `flow-implementer` サブエージェントが行う。
- メインエージェントは、サブエージェント起動、入力整理、成果物パス確認、結果要約、ユーザーへの次アクション提示だけを行う。
- サブエージェントを起動できない場合、メインエージェントは実装や `implement.md` 更新を直接行わず、再試行またはユーザーへの報告で停止する。

## 入力

ユーザー入力から以下を抽出する。

- 対象の `spec/{yyyymmdd_feature}/plan.md` または feature ディレクトリ名
- 実装対象タスク（全タスク / 特定タスク / 続きから）
- 制約・優先順位
- 検証に関する指定

引数が曖昧な場合は、`spec/**/plan.md` を確認して候補を提示する。

## 成果物

- 実装変更: `plan.md` に記載された対象ファイル
- テスト変更: `plan.md` または既存規約に基づくテストファイル
- 進捗ファイル: `spec/{yyyymmdd_feature}/implement.md`

## ワークフロー

### 1. 作業前確認

1. `git status --short` で作業ツリーを確認する。
2. `AGENTS.md` を読み、リポジトリ規約、検証コマンド、禁止事項を確認する。
3. 対象の `plan.md` と、同じディレクトリにある `design.md` があれば読む。
4. `plan.md` の `承認状態`、実行サマリ、変更ファイル一覧、変更ファイル詳細、タスク分解、詳細手順、検証方法、実装引き継ぎチェックを確認する。
5. `plan.md` の `承認状態` が `Approved` でない場合、実装を開始してはいけない。必要に応じて `implement.md` にはブロック理由の記録だけを行い、ユーザーへ承認を求める。
6. `実装引き継ぎチェック` がない、または `NG` / 未記入 / 根拠不足 / 矛盾を含む場合は、実装を開始してはいけない。
7. 変更ファイル詳細に必要な関数名、メソッド名、export 名、
   input/output、エラー時の扱い、既存コードとの接続箇所がない場合は、
   実装を開始してはいけない。
   該当しない項目が `該当なし` で理由つきなら開始してよい。
8. 各タスクの対象ファイル、依存関係、完了条件、検証方法が不足している場合は、実装を開始してはいけない。
9. `plan.md` が承認済みでも実装に必要な情報が不足している場合は、実装前にユーザーへ確認する。
10. plan にない判断事項、入力条件、制約、差分が見つかった場合は、実装前ブロックとして扱う。
11. ユーザー確認が必要な場合は、`次に取るべきステップ` を「ユーザーがブロック事項に回答する」とし、実装完了扱いにしない。

### 2. 進捗ファイル作成

`spec/{yyyymmdd_feature}/implement.md` がなければ作成する。既にある場合は続きを更新する。
既存の `implement.md` がある場合は、`状態`、`タスク進捗`、`変更サマリ`、
`検証ログ`、`補足・計画との差分`、`次に取るべきステップ` を確認し、
未完了タスクまたはユーザーの最新依頼から再開する。

```md
# 実装記録: {feature}

## メタデータ
- 日付: {yyyy-mm-dd}
- 機能: {feature}
- 計画: {plan.md path}
- 状態: In Progress

## タスク進捗
| ID | タスク | 状態 | ファイル | 検証 |
| --- | --- | --- | --- | --- |
| T1 |  | Pending |  |  |

## 変更サマリ
| 区分 | ファイル | 対応内容サマリ |
| --- | --- | --- |
| 追加 |  |  |
| 修正 |  |  |
| 削除 |  |  |

## 変更履歴
| 日時 | イベント | 内容 |
| --- | --- | --- |
| {yyyy-mm-dd HH:MM} | Started | 実装を開始 |

## 検証ログ
| 日時 | コマンド | 結果 | 内容 |
| --- | --- | --- | --- |

## 補足・計画との差分
- 

## 次に取るべきステップ
- ステップ:
- 理由:
- ユーザーに提示する文言:
```

### 3. 実装

1. 依存関係順にタスクを実行する。
2. 各タスクの開始時に `implement.md` の状態を `In Progress` にする。
3. 既存コードやドキュメントのパターンに合わせて実装する。
4. 計画から外れる必要がある場合は、理由と影響を `補足・計画との差分` に記録する。
   ただし、plan にない判断事項、入力条件、制約、差分はそのまま実装してはいけない。
   これらはブロック理由として記録し、ユーザー確認へ回す。
5. タスク完了時に `implement.md` の状態、変更ファイル、検証方法を更新する。
6. 実装結果に合わせて `変更サマリ` を追加・修正・削除の区分ごとに更新する。該当なしの区分は `なし` と書く。
7. 内部変数名、import 順、軽微な整形、既存規約へ合わせるための小さな調整は、plan の意味を変えない範囲で実装裁量として扱ってよい。
8. 公開 API、責務、input/output、エラー挙動、対象範囲、検証範囲が変わる場合は、実装裁量ではなく plan 外判断として停止する。

### 4. 検証

1. `AGENTS.md`、`plan.md`、既存設定から検証コマンドを選ぶ。
2. ドキュメント変更では Markdown lint や整合性確認を優先する。
3. k6 実装を追加した場合は、必須環境変数と小規模スモークの観点を確認する。
4. 実行したコマンド、結果、未実行理由を `検証ログ` に記録する。
5. 失敗した場合は原因を調べ、修正できる範囲なら修正して再検証する。原因が不明または方針判断が必要なら停止してユーザーへ報告する。
6. 検証中に plan にない判断事項や入力条件が判明した場合は、追加実装せず、ブロックとして記録してユーザー確認へ回す。

### 5. 完了

以下を満たしたら `implement.md` の `状態` を `Completed` にする。

- 対象タスクが完了している。
- 変更ファイルが `plan.md` のスコープ内に収まっている。
- plan にない差分を、ユーザー確認なしに実装していない。
- 追加・修正・削除で区分した変更サマリが記録されている。
- 必要な検証が実行済み、または未実行理由が明記されている。
- 未完了事項やリスクが最終報告に含まれている。
- `次に取るべきステップ` が記録されている。

代表的な次アクション:

| 状態 | 次に取るべきステップ | ユーザーに提示する文言の方向性 |
| --- | --- | --- |
| plan 未承認、実装引き継ぎチェック不備、または実装前ブロック | ユーザーがブロック事項に回答する | 何が不足しているかを示し、回答を求める。 |
| 実装完了、一部検証未実施 | ユーザーが結果を確認し、必要なら追加検証条件を渡す | 未実施理由と追加で必要な入力を明記する。 |
| 実装・検証完了 | ユーザーが結果を確認する | 完了内容、検証結果、残リスクを確認してもらう。 |

### 6. 追加作業の再委譲

実装完了後に追加検証、環境準備、レビュー修正、タスク状態更新、
実行ログ追記が必要になった場合は、可能な限り同じ
`flow-implementer` サブエージェントに追加入力して行う。
メインエージェントは既存 `plan.md`、既存 `implement.md`、
ユーザーの最新依頼、実行してよい範囲だけを渡す。
既存サブエージェントが利用できない場合だけ、新しい `flow-implementer` を起動し、
既存 `plan.md` / `implement.md` とユーザー最新入力から再開する。

## 行動指針

- 既存変更を勝手に戻さない。
- `plan.md` が未承認の場合は実装しない。
- `承認状態: Approved` だけで実装開始可と判断しない。
- `実装引き継ぎチェック` と詳細手順を読み、実装者が迷わず実行できる情報が揃っているか確認する。
- 実装前に対象ファイルと既存パターンを読む。
- 不明点を推測で埋めず、必要に応じて質問する。
- plan にない判断事項、入力条件、制約、差分は推測で実装しない。
- 軽微な既存 helper への合わせ込み、typo、明白な import 修正は継続してよいが、判断が必要な差分は停止する。
- 変更は計画に沿って小さく進め、検証可能な単位で確認する。
- `results/` やシークレット、実行結果の生データをコミット対象にしない。
- 出力は日本語で記述する。
- 完了時は、ユーザーが結果確認、追加検証条件の提示、レビュー修正依頼のいずれを行うべきかを明記する。

## 完了条件

- `spec/{yyyymmdd_feature}/implement.md` が存在する。
- 実装済みタスク、変更ファイル、検証結果が記録されている。
- 必要な実装とテストまたはドキュメント更新が完了している。
- 実装開始前に `承認状態: Approved` と `実装引き継ぎチェック` を確認している。
- plan にない差分がある場合は、Completed にせずブロックとして記録されている。
- 作業後の `git status --short` を確認している。
- `次に取るべきステップ` が明記されている。

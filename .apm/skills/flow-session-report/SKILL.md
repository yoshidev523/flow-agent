# Flowセッションレポート

## 入力と対象

Flowから対象repository、feature directory、完了チェックポイントのcommit SHA、
現在のImplement review cycleとコードsnapshot（base/head）を受け取る。
チェックポイントにある `flow-state.yml` の `phase` と `state` が `completed` であることを確認する。
`artifacts.implement` と `reviews.implement` が指すファイルを同じcommitから読み、
レビュー対象・cycle・コードsnapshotが依頼内容および `completed` のImplementと一致し、
レビュー結果が `passed` であることを確認する。
対象や参照が確認できなければ、既存HTMLを上書きせず理由を返す。

完了チェックポイントの要求、Design・Plan・Implement、該当review、採用済みfeedback、
`audit.md` を読む。実際の変更は渡されたbaseからheadまでのGit差分で確認する。
過去の判断を参照するときは採用後の訂正や再計画を照合し、最終版と混同しない。
差分から確認できる振る舞いと、記録で裏付けられる採用理由を区別する。
記録のない判断は「理由の記録なし」とし、実際に比較した案だけを載せる。

## 内容と出力

[HTMLテンプレート](assets/session-report.html)を使い、次を日本語でまとめる。

- 利用者や保守担当者に何ができるようになったか。
- 処理、データ、責務の変化が分かる前後比較。複数の変更は目的ごとにまとめ、簡潔な文章と必要な図で説明する。
- 主要な判断の背景、採用理由、記録のある代替案とその得失。削除・置換では元の振る舞いや責務の行き先と影響。
- 必須検証の結果、最終レビューの結果、残る制約や未確認事項。
- 対象の実装commit、review cycle、完了チェックポイント。各説明から成果物の節、判断ID、監査event ID、
  または対象commit上のファイル・行をたどれるようにする。

監査や会話を全文転載せず、判断に必要な情報だけを抽出する。認証情報、機密、個人情報を転記しない。
資料由来の文字列はHTMLとして解釈されないようにエスケープする。リンクは確認済みの相対参照かHTTPSに限定する。
図はHTML/CSSで作り、スタイルも同梱する。外部アセットやJavaScriptを必要としない。

### 変更に応じた図解

生成時は[レポート全体のサンプル](assets/session-report-example.html)を読み、文章・前後比較・判断理由・検証結果の組み合わせ方を参照する。
図を使う場合は[図の種類別サンプル](assets/diagram-samples.html)の対応する節とCSSも読み、図の構造・接続・ラベル・読み方の表現を参照する。
種類別サンプルにはフローチャート、シーケンス図、ER図、コンポーネント図、依存関係図を同梱する。
サンプルは構成と表現の参考とし、題材・判断理由・検証結果を実際の完了証拠として転用しない。
必要なHTML/CSSだけを出力へ取り込み、説明対象に合わせて組み替える。出力をスキル内のサンプルや一時pathに依存させない。

各変更には、何をどう変え、どのような効果や影響があるかを簡潔な文章で必ず説明する。
図を載せる場合も文章を省略せず、各図に何を読み取れるかの短い説明を添える。
主要な変更は、伝えたい関係に合う図を選んで説明する。次を目安にし、全種類を載せる必要はない。

| 伝えたい変更 | 図の候補 |
| --- | --- |
| システム全体、外部サービス、実行環境のつながり | システム構成図・配置図 |
| 処理の順序や条件分岐 | フローチャート |
| 利用者・サービス間のやり取りと順序 | シーケンス図 |
| 状態と遷移条件 | 状態遷移図 |
| データの加工・受け渡し・保存先 | データフロー図 |
| エンティティやクラスの構造と関係 | ER図・クラス図 |
| モジュールの責務や依存関係 | コンポーネント図・依存関係図 |
| 画面間の導線や画面内の配置 | 画面遷移図・ワイヤーフレーム |

複数の変更は目的ごとに説明を分け、それぞれに必要な数・種類の図を使う。
一つの変更にも、構成図とシーケンス図など、異なる観点を補う複数の図を組み合わせてよい。
図の数は固定せず、理解に必要な観点を選び、同じ内容の重複は避ける。
前後比較をする図は、比較の組ごとに変更前と変更後を同じ種類・粒度・用語・向きで並べる。
ノードと線、矢印、枠などで関係を描き、箇条書きを並べるだけの比較にしない。
図のタイトルには何の変化を示すかを書き、接続には呼び出し・データ・依存・遷移条件などの意味を付ける。
追加・削除・移動した要素は文字や枠線でも区別し、色だけに頼らない。必要な凡例と短い読み方、根拠への参照を添える。
複雑な変更は概要図と必要な詳細図に分け、比較に必要な周辺要素だけを含める。

新規機能で対応する変更前がなければ「該当機能なし」と明示し、確認できる既存の流れがあれば図示する。
変更前の根拠が不足する場合は不足を明示し、確認できた範囲だけを描く。関係を推測で補わない。
文言修正など図が理解に寄与しない変更は、簡潔な文章だけで説明してよい。必要なら表を添える。
テンプレートの図は構造例として使い、選んだ図に合わせて組み替える。

完成したUTF-8 HTMLを同じdirectory内の一時ファイルに書いて内容と参照を確認する。
各変更の文章による説明と各図の短い説明、図と差分の整合、矢印とラベルの対応、狭い画面での可読性も確認する。
確認後、`artifacts/session-report.html` へ置き換える。対象feature配下の実ファイルであることを確認する。
失敗時は一時ファイルを片付け、以前の完全なHTMLを保持する。Flowへ出力pathと対象の識別情報、
または失敗理由を返す。状態・監査・既存の成果物・コードは編集せず、Git保存はFlowへ任せる。

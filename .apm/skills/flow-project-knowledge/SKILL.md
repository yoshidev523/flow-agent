# Flow Project Knowledge

## 責務と入力

入力は対象project・対象範囲、操作（把握／更新判断・乖離チェック／採用済み更新）、
要求・決定事項・人間feedback・AIレビュー指摘と根拠。既存の「更新提案」の依頼も更新判断として扱う。
Flowからは`flow-project-knowledge-agent`がこのスキルを使い、判断と提案を呼出側へ返す。
更新判断・乖離チェックは読み取り専用とし、採用済み更新が指定された場合だけ文書を編集する。
Flowの状態遷移、review判定、Design・Plan・Implementの編集を行わない。
把握結果は呼出側へ返し、成果物のownerが自分の成果物へ保存する。
単独利用では同じ内容をチャットで返す。中継request/result契約やルールの複製台帳を作らない。

## 把握と適用材料

1. 対象projectと変更予定範囲に適用されるAGENTS.mdを確認する。Planで対象が増えた場合や
   Implementで対象fileが具体化した場合は、配下のAGENTS.mdも再確認する。
2. AGENTS.mdから参照される規約、設計・実装方針、決定記録を、そのprojectの文書運用に沿って読む。
   正本は同directoryのMarkdownに限定しない。別repository・文書service・共有文書も対象とする。
   関係する参照だけを辿り、無関係な文書を網羅的に収集しない。
3. 明示された必須ルール、推奨・慣習、過去判断の背景、コードからの仮説、今回限りの例外を区別する。
   根拠箇所・適用範囲・成立前提を示す。コードの多数派や過去の一事例だけで必須化しない。
4. 文書間の矛盾・古い前提・アクセス不能を記録する。既存の指示優先順位とprojectの運用を守る。
   必須判断に影響する不明点は呼出側へ返し、任意資料の欠落だけで全工程を止めない。
5. 文書の識別子、正本のlocation、適用範囲、取得版、取得内容のSHA-256、確認内容と根拠を返す。
   ローカルfileは絶対path、外部文書は正本のURLまたはservice URIを使う。
   外部文書のdigestは実際に取得した内容から計算し、版番号から推測しない。
   未取得文書はunavailableとし、digestはnull。参照不能な正本の代替を勝手に作らない。

呼出側の工程に合う具体度へ絞る。DesignはWHAT・制約・受け入れ条件、PlanはHOW・タスク・検証、
Implementは対象fileの規約と実際の検証を扱う。Designでコードの細部を要求しない。
既存方針は背景を含めて理解し、変更可能な選定を不変の必須制約へ変換しない。

Flow成果物へ保存する場合の形式は[project_knowledge契約](../flow/references/project-knowledge.md)を使う。
把握だけでは適合と断定せず、実際の成果物との照合が未実施ならunverifiableと理由を返す。
文書がない場合も探索範囲と「該当ルールなし」の根拠を示す。空の配列だけを返さない。

## 更新判断と実装・ドキュメントの乖離チェック

決定事項・人間feedback・AIレビュー指摘を既存文書、関連するコード・設定・テスト、
現在の成果物と照合する。対象の参照・版と根拠箇所を示し、変更の影響範囲に絞って確認する。
ルール・ナレッジへの反映要否と、実装・文書の同期要否を別々に判断する。
決定や対応が未確定でも現時点の結果を返し、修正・判断の確定後は変更された範囲を再確認する。

乖離チェックでは次を区別する。

- 文書更新が必要: 採用済み判断や要件に実装が適合し、文書が古い・不足している。
- 実装修正が必要: 有効な要件・規約に実装が反している。文書を書き換えて適合扱いにしない。
- 判断が必要: 実装・文書・採用済み判断が矛盾し、どの方針へ揃えるか未確定。
- 同期不要: 確認範囲では一致している、または今回の変更が文書へ影響しない。根拠を示す。
- 確認不能: 必要な文書・実装・検証証拠が未取得または未作成。同期不要へ読み替えない。

実装前の工程では現在存在する実装だけを照合し、未実装の計画を実装済みと扱わない。
複数の対応が必要なら対象ごとに区別する。コードの現状やAI指摘だけで正しい方針を確定しない。
AIのgateとscope_candidateを区別し、後者を恒久ルールや実装修正の採用済み判断に変換しない。
コードの修正は行わず、現在工程の修正や上流への再計画が必要な影響を呼出側へ返す。

## 更新提案と返却

再利用できる新しい判断・曖昧な基準の具体化・文書の矛盾がある場合にだけ提案する。
すでに記載済み、根拠不足、今回限りの例外、未解決判断はその理由を返し、提案を水増ししない。
提案しない場合も、対象の決定事項・feedback・指摘、ルール・ナレッジへの反映要否と理由、
乖離チェックの結果と根拠、未確認事項、現在タスクへの影響を呼出側へ返す。
Flowはその検討結果をチャットへ表示し、単独利用ではこのスキルが同じ内容を返す。

提案には次を含める。

- 根拠となる決定事項・feedback・指摘と、将来のどの場面で役立つか、または解消する文書の乖離。
- 必須／推奨／背景／例外の区別、適用条件、例外、既存規約との整合。
- projectの文書運用に沿った正本の更新先と具体的な差分。AGENTS.mdは短い入口を保つ。
- 現在のDesign・Plan・実装への影響と、更新が未採用であること。

提案は呼出側へ返し、文書のreview・保存手順はprojectの運用に従う。
Flowはチャットで差分と正本へのlinkを提示し、提案・採否の要点を既存actionイベントへ記録する。
成果物作成中に得た候補は、そのownerが本文の「知識の更新候補」へ残せる。
候補は必須質問・scope_candidateと別に扱い、文書更新の採否待ちだけで進行を止めない。
乖離チェックはreviewの代替ではなく、review status・retry・human mode切替を変更しない。

## 採用済み更新

利用者がルール・ナレッジの恒久化または実装に合わせた文書同期の内容・範囲を採用した場合、
または「今後もこの方針で、規約へ反映」のように明示した場合だけ更新する。
今回の実装修正への同意を恒久ルールや文書更新への同意に読み替えない。
すでに更新が明示されていれば同じ確認を繰り返さない。

正本の現在版と差分を照合し、既存の文書owner・review・権限・保存手順に従って更新する。
外部serviceでは対応connectorを優先し、利用不能なら具体的な差分を返して未反映と報告する。
同じ文書を他の実行主体と同時編集しない。Flow成果物やauditは直接編集しない。
更新前後の参照、反映内容、未反映事項、現在タスクへの影響を返す。
現在タスクの要件・Planが変わる場合の再計画はFlowまたは単独利用の呼出側が判断する。

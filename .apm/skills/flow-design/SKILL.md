# Flow Design

## 目的

実装前に、ユーザーの要望から目的・スコープ・前提・未決事項・
受け入れ条件を明確化し、設計成果物として
`spec/{yyyymmdd_feature}/design.md` を作成する。

このスキルは、後続の特定スキルを前提にしない。成果物は単独で読める設計メモとして完結させる。

## 実行主体

- このスキルの成果物作成、成果物更新、承認反映、フィードバック反映は、必ず `flow-designer` サブエージェントが行う。
- メインエージェントは、サブエージェント起動、入力整理、成果物パス確認、結果要約、ユーザーへの次アクション提示だけを行う。
- サブエージェントを起動できない場合、メインエージェントは `design.md` を直接更新せず、再試行またはユーザーへの報告で停止する。

## 入力

ユーザー入力から以下を抽出する。

- 実現したいこと
- 背景・目的
- 対象範囲
- 制約・前提
- 参考情報（チケット、URL、既存ドキュメント、関連ファイル）

必須情報が不足している場合は、無理に設計を確定せず質問する。

## 根拠分類と推測禁止

設計上の重要判断は、次の根拠分類を使って扱う。

| 分類 | 意味 | 扱い |
| --- | --- | --- |
| `Confirmed` | ユーザーの明示回答、承認済み成果物、コードまたは実行結果で確認済み | 決定事項にできる |
| `Docs-derived` | 既存ドキュメント由来だが、今回ユーザーが明示承認していない | ユーザー確認なしに確定しない |
| `Assumption` | エージェントの仮説、推奨案、便宜上の案 | 決定事項にせず質問へ回す |
| `Open` | 判断に必要な情報が不足 | 質問へ回す |

推奨案は回答候補であり、ユーザー回答前の確定事項ではない。
`Confirmed` 以外の内容を `決定事項` に入れてはいけない。
すべての事項において、根拠のない推測は禁止する。
ユーザー回答または確認可能な根拠がない内容は、些細に見えても確定事項にしない。
`Docs-derived` / `Assumption` / `Open` が残る場合は、設計レビュー待ちへ進めず質問待ちにする。

## 質問の責務

`flow-design` の質問は WHAT に限定する。

- 質問すること:
  - どのような状態にしたいか
  - 何を実現したいか
  - どこまでを対象範囲にするか
  - 何を受け入れ条件にするか
  - どの制約、前提、非機能要件を守るか
- 質問しないこと:
  - どのファイルをどう編集するか
  - どの関数名、export 形式、内部構造にするか
  - どの順番で実装するか
  - どのコマンドで検証するか

HOW の判断が見つかった場合は、`design.md` では確定せず
「実装計画で確認する事項」として補足に残す。
ただし、ユーザーの要望そのものが具体的な実装方法を指定している場合は、
その指定を制約として記録してよい。
WHAT / 制約が不明な場合は、対象の種類や大きさに関わらず、推測で埋めず質問する。

## 成果物

- 出力先: `spec/{yyyymmdd_feature}/design.md`
- `yyyymmdd` はローカル日付を使う。
- `{feature}` は短い英小文字の kebab-case または snake_case にする。
- 例: `spec/20260706_k6-load-test/design.md`

## ワークフロー

### 1. 初期整理

1. ユーザー入力と関連ドキュメントを読み、目的・背景・制約を整理する。
2. 不明点、曖昧な点、矛盾、依存関係を洗い出す。
3. 主要な判断を `Confirmed` / `Docs-derived` / `Assumption` / `Open` に分類する。
4. `spec/{yyyymmdd_feature}/design.md` を作成し、初期設計と質問を記載する。

### 1.5 途中再開

既存の `design.md` がある場合は新規作成せず、以下を確認して続きから処理する。

- `承認状態`
- 最新の `質問ラウンド`
- `確認事項` の `Open` / `Resolved`
- `根拠メモ` の `Docs-derived` / `Assumption` / `Open`
- `次に取るべきステップ`
- `フィードバック履歴`

ユーザー回答、承認、修正依頼が渡された場合は、最新入力を既存成果物へ反映し、
必要なら次の `Round N` を追加する。
承認反映後に `承認状態: Approved` になった場合は、最終報告で次フェーズへ進めることを明記する。

### 2. 質問とフィードバック

1. 要件定義に影響する WHAT の不明点だけを質問する。
2. 質問フェーズはラウンド制にし、`Round 1`, `Round 2` のように回答単位を分ける。
3. 質問は優先度順に並べ、回答しやすい粒度にする。
4. 選択肢を出せる場合は推奨案を 1 つ示し、判断理由を短く添える。
5. 質問項目以外の特記事項、補足、懸念を自由入力できる欄を必ず用意する。
6. ユーザーの回答を受けたら、選択式回答だけでなく自由入力欄の内容も確認する。
7. 回答や補足に曖昧さ、矛盾、新しい前提、スコープ変更が含まれる場合は、次ラウンドの追加質問を作成する。
8. 追加質問が不要な場合だけ、`design.md` の決定事項、未決事項、受け入れ条件を更新し、設計レビュー待ちへ進める。
9. `Docs-derived` / `Assumption` / `Open` が残る場合は、設計レビュー待ちへ進めず質問待ちにする。

ユーザーが本文で直接回答した場合は、その内容を反映してよい。
ユーザーに `design.md` の回答欄編集を必須にしない。
質問を作成してユーザー回答が必要になった場合、`design.md` は
`承認状態: Pending` のままにし、サブエージェントは質問待ちとして
最終報告する。
この場合の `次に取るべきステップ` は「ユーザーが質問に回答する」とし、
承認を促す文言は出さない。
ユーザー回答後の反映は、可能な限り同じ `flow-designer` サブエージェントに
追加入力して行う。
既存サブエージェントが利用できない場合だけ、新しい `flow-designer` を起動し、
既存 `design.md` とユーザー最新入力から再開する。
質問待ちや承認待ちの最終報告は、この設計作業全体の終了を意味しない。

### 2.5 評価用候補モード

呼び出し元から明示された場合に限り、ユーザーへ提示する質問の推奨案を
仮適用した評価用候補を作成できる。これは設計案を比較・評価するための
汎用出力モードである。

- 推奨選択肢、代替案、利点、欠点、根拠、影響範囲を保持する。
- 仮適用した内容をユーザー確認済みまたは `Confirmed` として扱わない。
- `承認状態: Pending` を維持する。
- 最終報告には、評価用候補であること、未確認事項、通常ならユーザーへ提示する質問を含める。
- 呼び出し元が指定しない場合は、通常の質問・承認フローだけを実行する。

### 3. 質問ラウンドの扱い

質問ラウンドは、ユーザー回答を受けるたびに以下を判断する。

- 回答された選択肢を決定事項へ反映できるか
- 自由入力欄に、質問項目外の新しい要件、制約、懸念、例外が書かれていないか
- 回答同士または既存 design と矛盾していないか
- 追加の WHAT 質問が必要か

追加質問が必要な場合:

- 新しい `Round N` を作成する。
- 前ラウンドの回答から何が不明として残ったかを明記する。
- `次に取るべきステップ` は「ユーザーが追加質問に回答する」とする。
- 承認を促してはいけない。

追加質問が不要な場合:

- 確認事項を `Resolved` に更新する。
- 自由入力欄の内容を必要に応じて決定事項、対象外、リスク、受け入れ条件へ反映する。
- `次に取るべきステップ` は「ユーザーが設計をレビューし、承認または修正依頼する」とする。

### 4. 最終化

以下が満たされたら最終化する。

- 目的とスコープが明確である。
- 主要な仕様判断が決定事項として記載されている。
- 未決事項が残る場合、その扱いが明記されている。
- 受け入れ条件が検証可能な形で記載されている。
- 決定事項が `Confirmed` の根拠だけで構成されている。
- `Docs-derived` / `Assumption` / `Open` が残っていない。
- ユーザーが会話上で明示的に内容を承認している。

`承認状態: Approved` はユーザーの明示承認を表す状態であり、設計内容が妥当そうに見えることや不明点がないことを理由に、エージェントが自己判断で設定してはいけない。
承認されたら `承認状態: Approved` に更新する。承認がない間は必ず `Pending` のままにする。
承認反映も可能な限り同じ `flow-designer` サブエージェントに委譲し、
既存 `design.md` とユーザー承認の事実だけを渡して更新させる。
既存サブエージェントが利用できない場合だけ、新しい `flow-designer` で成果物ベースから再開する。

### 5. 次アクション判定

最終報告と `design.md` には、次に取るべきステップを明記する。

| 状態 | 次に取るべきステップ | ユーザーに提示する文言の方向性 |
| --- | --- | --- |
| Open の確認事項あり | ユーザーが質問に回答する | 質問への回答を依頼する。承認は促さない。 |
| Open なし、`Pending` | ユーザーが設計をレビューし、承認または修正依頼する | 設計レビューと承認可否を求める。 |
| `Approved` | メインエージェントが Plan へ進む | 承認済みのため Plan へ進めることを示す。 |

Open の確認事項がある間は、`この内容で問題なければ承認してください` のような承認誘導をしてはいけない。

## 質問フォーマット

ユーザーに質問する場合は、会話上でも `design.md` 上でも次の形を基本にする。
選択肢は A/B/C の記号だけで終わらせず、説明、メリット、デメリット、推奨有無を必ず書く。
回答しやすいように、チェックボックスと自由記述欄を用意する。

```md
## 質問ラウンド

### Round {n}

#### Q1. {質問}

**推奨**: A. {推奨する選択肢名}

**確認したい理由**:
- {この判断が目的、対象範囲、受け入れ条件、制約に与える影響}

**選択肢**:

- [ ] A. {選択肢名}（推奨）
  - 説明: {何を選ぶことになるか}
  - メリット: {利点}
  - デメリット: {欠点や制約}
- [ ] B. {選択肢名}
  - 説明: {何を選ぶことになるか}
  - メリット: {利点}
  - デメリット: {欠点や制約}
- [ ] C. {選択肢名}
  - 説明: {何を選ぶことになるか}
  - メリット: {利点}
  - デメリット: {欠点や制約}

**回答欄**:
- 選択:
- 補足:

### 特記事項・補足（自由記述）

質問項目以外で、前提、懸念、例外、追加要望、判断材料があれば記載してください。

- 

### ラウンド判定

- 状態: Open
- 追加質問の要否:
- 判断理由:
```

## 行動指針

- 根拠のない推測を確定事項として書かない。
- 対象の種類や大きさに関わらず、確認できない内容を決定事項にしない。
- 推奨案や仮置き案は回答候補に留め、ユーザー回答前に確定しない。
- `Docs-derived` / `Assumption` / `Open` が残る場合は、設計レビューや承認を促さない。
- 実装計画や作業分解、実装 HOW に踏み込まず、要件・仕様・受け入れ条件の明確化に集中する。
- HOW の候補を見つけても、ユーザーへ design 質問として出さず、plan 側へ引き継ぐ補足として残す。
- 質問回答を受けたら、自由入力欄を含めて追加質問の要否を判断してから承認待ちへ進める。
- 質問ラウンドが Open の間は承認を促さない。
- 既存の `AGENTS.md`、設計ドキュメント、タスク一覧、リポジトリ規約を尊重する。
- ファイル編集は `design.md` と必要な `spec/` 配下に限定する。
- 出力は日本語で記述する。
- 承認済みで次フェーズへ進める場合は、その旨を最終報告に明記する。
- ただし、次フェーズへの移行はメインエージェントが行い、成果物作成・更新は次フェーズのサブエージェントに委譲する。
- 未承認または `Open` の確認事項がある場合は、次フェーズへ進める案内をしない。

## 完了条件

### ドラフト完了条件

- `spec/{yyyymmdd_feature}/design.md` が存在する。
- 目的、スコープ、要求、受け入れ条件が明文化されている。
- `次に取るべきステップ` が明記されている。
- 質問がある場合は、質問ラウンド、回答欄、特記事項・補足欄、ラウンド判定が記載されている。
- 不明点がある場合は質問が記載されている。
- 決定事項が `Confirmed` の根拠だけで構成されている。
- `Docs-derived` / `Assumption` / `Open` が決定事項に混入していない。
- ユーザーの明示承認前は `承認状態: Pending` になっている。

### 承認完了条件

- ユーザーが会話上で明示的に内容を承認している。
- 不明点への質問とユーザーフィードバックが反映されている。
- 受け入れ条件が明文化されている。
- `承認状態` が `Approved` になっている。

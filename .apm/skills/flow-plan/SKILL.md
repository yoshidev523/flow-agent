# Flow Plan

## 目的

与えられた要件、または `spec/{yyyymmdd_feature}/design.md` をもとに、
実装者が着手できる粒度の詳細計画を作成し、
`spec/{yyyymmdd_feature}/plan.md` に保存する。

このスキルは、後続の特定スキルを前提にしない。成果物は単独で読める実装計画として完結させる。
`plan.md` は、後続の implementer が基本的に迷わず、プロジェクトの実装ルールに沿って順番に実行できる情報量にする。
ただし全変更を過剰に詳細化せず、実装判断が分岐しそうな点を plan 側で決める。

## 実行主体

- このスキルの成果物作成、成果物更新、承認反映、フィードバック反映は、必ず `flow-planner` サブエージェントが行う。
- メインエージェントは、サブエージェント起動、入力整理、成果物パス確認、結果要約、ユーザーへの次アクション提示だけを行う。
- サブエージェントを起動できない場合、メインエージェントは `plan.md` を直接更新せず、再試行またはユーザーへの報告で停止する。

## 入力

ユーザー入力から以下を抽出する。

- 対象の `spec/{yyyymmdd_feature}/design.md` または feature ディレクトリ名
- 実現したい要件や変更内容
- 制約・前提
- 参考情報（チケット、URL、既存ドキュメント、関連ファイル）

`design.md` が指定されていない場合は、ユーザー入力から feature 名を決めて
`spec/{yyyymmdd_feature}/plan.md` を作成してよい。
ただし、要件が不足している場合は計画を確定せず質問する。

## 根拠分類と推測禁止

実装方針に関わる判断は、次の根拠分類を使って扱う。

| 分類 | 意味 | 扱い |
| --- | --- | --- |
| `Confirmed` | ユーザーの明示回答、承認済み design / plan、コードまたは実行結果で確認済み | 実装方針にできる |
| `Docs-derived` | 既存ドキュメント由来だが、今回ユーザーが明示承認していない | ユーザー確認なしに確定しない |
| `Assumption` | エージェントの仮説、推奨案、便宜上の案 | 実装方針にせず質問へ回す |
| `Open` | 判断に必要な情報が不足 | 質問へ回す |

推奨案は回答候補であり、ユーザー回答前の確定事項ではない。
すべての事項において、根拠のない推測は禁止する。
ユーザー回答または確認可能な根拠がない内容は、些細に見えても実装方針にしない。
`Docs-derived` / `Assumption` / `Open` を実行サマリ、変更ファイル一覧、変更ファイル詳細、タスク分解、詳細手順、実装引き継ぎチェックの確定内容に入れてはいけない。
`Docs-derived` / `Assumption` / `Open` が残る場合は、計画レビュー待ちへ進めず HOW 質問待ちにする。

## 質問の責務

`flow-plan` の質問は HOW に集中する。
承認済み `design.md` で WHAT が確定していても、実装計画では別観点として
HOW の未決事項を必ず棚卸しする。

- 質問すること:
  - どのファイル、モジュール、責務分担で実装するか
  - API 形状、関数名、export 形式、データ構造をどうするか
  - 既存コードへどう接続し、どの順序で変更するか
  - 検証コマンド、確認範囲、未実施時の扱いをどうするか
  - 複数の実装方法があり、保守性や後続タスクに影響する選択
- 原則:
  - design の質問回答を理由に HOW 質問を省略しない。
  - 追加質問が不要な場合でも、`確認事項` に「HOW 確認観点」と「質問不要と判断した理由」を明記する。
  - 複数の妥当な実装案があり、どれを選んでもよい状態なら質問する。
  - 既存規約、承認済み design、または明示指示で HOW が一意に決まる場合だけ質問不要にできる。
  - 対象の種類や大きさに関わらず、根拠が `Confirmed` でない限り質問する。

## 計画詳細度の基準

plan は変更種別に応じて詳細度を調整する。
常に全項目を埋めるのではなく、implementer が実装判断で迷う可能性がある情報を明確化する。

| 変更種別 | plan に必ず含める情報 |
| --- | --- |
| ドキュメント修正 | 対象ファイル、修正する見出しまたは記載箇所、整合性確認対象、検証方法 |
| 小さな helper / module 追加 | ファイル名、公開名、input/output、エラー時の扱い、呼び出し元、検証方法 |
| 既存関数やシナリオの修正 | 対象ファイル、変更する関数または処理ブロック、変更前後の責務、接続箇所、互換性、検証方法 |
| 共有モジュール / API 形状変更 | 責務分担、公開 API、データ構造、入出力、例外、接続点、互換性、検証方法 |
| 複数ファイル横断の変更 | ファイルごとの役割、変更順序、依存関係、タスク単位の完了条件、統合確認方法 |

plan で決めるべきもの:

- 公開される名前、関数名、メソッド名、export 名
- 対象ファイルとファイルごとの変更内容
- input、output、データ構造、エラー時または未設定時の扱い
- 既存コードとの接続箇所、呼び出し元、依存関係
- タスク順序、各タスクの完了条件、検証方法
- plan 外判断が必要になったときの停止条件

implementer に任せてよいもの:

- 内部変数名
- import 順や軽微な整形
- plan の意味を変えない明白な typo 修正
- 既存規約へ合わせるための小さな実装上の調整

上記の裁量であっても、公開 API、責務、入出力、エラー挙動、対象範囲、検証範囲が変わる場合は plan 側で決めるか、質問へ回す。

## 成果物

- 出力先: `spec/{yyyymmdd_feature}/plan.md`
- `design.md` が `spec/{yyyymmdd_feature}/design.md` にある場合は同じディレクトリへ出力する。
- `yyyymmdd` はローカル日付を使う。
- `{feature}` は短い英小文字の kebab-case または snake_case にする。
- 例: `spec/20260706_k6-load-test/plan.md`

## ワークフロー

### 1. 入力確認

1. 指定された design ファイル、feature ディレクトリ、または要件本文を確認する。
2. `AGENTS.md` と関連ドキュメントを読み、リポジトリ規約と配置方針を把握する。
3. 計画作成に必要な目的、スコープ、制約、受け入れ条件を抽出する。
4. HOW の未決事項を design とは別観点で棚卸しする。
5. 主要な HOW 判断を `Confirmed` / `Docs-derived` / `Assumption` / `Open` に分類する。
6. 変更種別に応じて、必要な計画詳細度を決める。
7. 実装者が迷いやすい公開名、input/output、エラー挙動、接続箇所、検証方法を棚卸しする。
8. 不明点や `Assumption` が実装方針に影響する場合は、`plan.md` に質問を記載し、ユーザーへ回答を求める。
9. 質問が不要な場合も、どの HOW 観点を確認し、なぜ質問不要と判断したかを `確認事項` に記載する。

### 2. コードベース分析

1. `rg --files` で構成を把握する。
2. 設計や要件に関係する既存ファイル、ドキュメント、テスト、設定を探す。
3. 既存の命名、配置、テスト、検証コマンドのパターンを抽出する。
4. 関連が薄いファイルを広く読みすぎず、計画に必要な範囲に絞る。

### 2.5 途中再開

既存の `plan.md` がある場合は新規作成せず、以下を確認して続きから処理する。

- `承認状態`
- 最新の `質問ラウンド`
- `確認事項` の `Open` / `Resolved`
- `根拠メモ` の `Docs-derived` / `Assumption` / `Open`
- `実行サマリ`
- `変更ファイル一覧`
- `変更ファイル詳細`
- `タスク分解`
- `詳細手順`
- `実装引き継ぎチェック`
- `次に取るべきステップ`
- `フィードバック履歴`

ユーザー回答、承認、修正依頼が渡された場合は、最新入力を既存成果物へ反映し、
必要なら次の `Round N` を追加する。
承認反映後に `承認状態: Approved` になった場合は、最終報告で次フェーズへ進めることを明記する。

### 3. 初版 plan.md 作成

`plan.md` には、計画の根拠、変更対象、タスク順序、検証方法を記載する。

不明点が残る場合は、質問を `確認事項` に記載し、`承認状態: Pending` のままにする。ユーザーが会話上で回答した場合は、その内容を反映してよい。
不明点が残らない場合でも、HOW 確認観点と質問不要理由を `確認事項` に記載する。

質問が必要な初版では、清書対象セクション（`実行サマリ`、`変更ファイル一覧`、`変更ファイル詳細`、`タスク分解`、`詳細手順`、`実装引き継ぎチェック`）を確定内容として作り込まない。
これらは質問回答で HOW が明確になり、追加質問が不要と判断したタイミングで清書する。
質問待ちの間は、各セクションを省略するか、「質問回答後に清書」と明記したプレースホルダーだけに留める。

### 4. フィードバック反映

1. ユーザーの回答やレビューコメントを確認する。
2. 質問フェーズはラウンド制にし、回答単位を `Round 1`, `Round 2` のように分ける。
3. 質問項目以外の特記事項、補足、懸念を自由入力できる欄を必ず確認する。
4. 回答や補足に実装方法、責務分担、検証方針、リスクの新しい論点が含まれる場合は、次ラウンドの追加質問を作成する。
5. 追加質問が不要な場合だけ、決定事項、タスク、検証方針、リスクを更新し、清書対象セクションを確定内容として作成してから計画レビュー待ちへ進める。
6. 清書後に `実装引き継ぎチェック` を実施し、すべて `OK` または根拠つきの `該当なし` にする。
7. 以下の場合は、計画レビュー待ちへ進めず質問待ちにする。
   - `Docs-derived` / `Assumption` / `Open` が残る。
   - `実装引き継ぎチェック` に `NG` / 未記入 / 矛盾がある。
8. ユーザーが会話上で明示的に計画を承認したら `承認状態: Approved` に更新する。

### 4.5 評価用候補モード

呼び出し元から明示された場合に限り、推奨 HOW を仮適用した完全な
評価用候補 plan を作成できる。これは実装案を比較・評価するための
汎用出力モードである。

- 代替案、利点、欠点、根拠、影響範囲を保持する。
- 実行サマリ、変更ファイル詳細、タスク、詳細手順、検証計画、
  実装引き継ぎチェックまで記述する。
- 仮適用した内容をユーザー確認済みまたは `Confirmed` として扱わない。
- `承認状態: Pending` を維持する。
- 最終報告には、評価用候補であること、未確認事項、通常ならユーザーへ提示する質問を含める。
- 呼び出し元が指定しない場合は、通常の質問・承認フローだけを実行する。

質問を作成してユーザー回答が必要になった場合、`plan.md` は
`承認状態: Pending` のままにし、サブエージェントは質問待ちとして
最終報告する。
この場合の `次に取るべきステップ` は「ユーザーが HOW 質問に回答する」とし、
承認を促す文言は出さない。
ユーザー回答後の反映は、可能な限り同じ `flow-planner` サブエージェントに
追加入力して行う。
既存サブエージェントが利用できない場合だけ、新しい `flow-planner` を起動し、
既存 `plan.md` とユーザー最新入力から再開する。
質問待ちや承認待ちの最終報告は、この計画作業全体の終了を意味しない。

`承認状態: Approved` はユーザーの明示承認を表す状態であり、計画内容が妥当そうに見えることや不明点がないことを理由に、エージェントが自己判断で設定してはいけない。
承認がない間は必ず `Pending` のままにする。
承認反映も可能な限り同じ `flow-planner` サブエージェントに委譲し、
既存 `plan.md` とユーザー承認の事実だけを渡して更新させる。
既存サブエージェントが利用できない場合だけ、新しい `flow-planner` で成果物ベースから再開する。

質問回答を受けた場合は、選択式回答だけでなく自由入力欄も読み、
追加質問の要否を判断する。追加質問が必要な間は承認を促してはいけない。

### 5. 質問ラウンドの扱い

質問ラウンドは、ユーザー回答を受けるたびに以下を判断する。

- 回答された選択肢を実装方針へ反映できるか
- 自由入力欄に、質問項目外の新しい HOW 判断、制約、懸念、例外が書かれていないか
- 回答同士、承認済み design、既存コード制約と矛盾していないか
- 追加の HOW 質問が必要か

追加質問が必要な場合:

- 新しい `Round N` を作成する。
- 前ラウンドの回答から何が不明として残ったかを明記する。
- `次に取るべきステップ` は「ユーザーが追加質問に回答する」とする。
- 承認を促してはいけない。

追加質問が不要な場合:

- 確認事項を `Resolved` に更新する。
- 自由入力欄の内容を必要に応じて実行サマリ、変更ファイル一覧、変更ファイル詳細、タスク分解、詳細手順、検証計画、リスクへ反映する。
- 清書対象セクションを、`Confirmed` の根拠だけで実装者が着手できる粒度に清書する。
- `実装引き継ぎチェック` を実施し、`NG` / 未記入 / 矛盾が残らないことを確認する。
- `次に取るべきステップ` は「ユーザーが計画をレビューし、承認または修正依頼する」とする。

### 6. 次アクション判定

最終報告と `plan.md` には、次に取るべきステップを明記する。

| 状態 | 次に取るべきステップ | ユーザーに提示する文言の方向性 |
| --- | --- | --- |
| Open の HOW 確認事項あり | ユーザーが質問に回答する | HOW 質問への回答を依頼する。承認は促さない。 |
| Open なし、`Pending` | ユーザーが計画をレビューし、承認または修正依頼する | 計画レビューと承認可否を求める。 |
| `Approved` | メインエージェントが Implement へ進む | 承認済みのため実装へ進めることを示す。 |

Open の確認事項がある間は、`この内容で問題なければ承認してください` のような承認誘導をしてはいけない。

- 1 つの `plan.md` に両方のテンプレートを混在させない。

## 行動指針

- 根拠のない推測を確定事項として書かない。
- 要件や設計が未確定の場合は、計画を断定せず確認質問を残す。
- 対象の種類や大きさに関わらず、確認できない内容を実装方針にしない。
- 推奨案や仮置き案は回答候補に留め、ユーザー回答前に確定しない。
- `Docs-derived` / `Assumption` / `Open` が残る場合は、計画レビューや承認を促さない。
- 承認済み design の WHAT 質問と、plan で扱う HOW 質問を混同しない。
- HOW の複数案が実装品質、保守性、後続タスクに影響する場合は、design で近い話題が回答済みでも質問する。
- 質問回答を受けたら、自由入力欄を含めて追加質問の要否を判断してから承認待ちへ進める。
- 質問ラウンドが Open の間は承認を促さない。
- 質問ラウンドが Open の間は、清書対象セクションを確定内容として作り込まない。
- 追加質問が不要になった時点で、清書対象セクションをまとめて清書してから計画レビュー待ちへ進める。
- レビュー待ちへ進む前に `実装引き継ぎチェック` を実施し、すべて `OK` または根拠つきの `該当なし` にする。
- `実装引き継ぎチェック` に `NG`、未記入、根拠不足、矛盾がある場合は、承認待ちにせず HOW 質問待ちへ戻す。
- 実装者がそのまま作業できるよう、タスクはファイル単位または検証可能な作業単位に分解する。
- 各タスクに目的、対象ファイル、依存関係、確認方法を含める。
- `実行サマリ` に方針、主要な成果物、検証方針を短く記載する。
- `変更ファイル一覧` に追加・修正・削除の区分ごとに対象ファイルと対応内容サマリを記載する。該当なしの区分は `なし` と書く。
- `変更ファイル詳細` に、変更種別に応じた公開名、input/output、
  エラー時の扱い、既存コードとの接続を記載する。
  該当しない項目は `該当なし` と書き、空欄にしない。
- 詳細手順には、implementer が plan 外の設計判断をしなくてよい粒度で、対象ファイル、追加・変更する要素、入出力、挙動、完了条件を記載する。
- 既存の `AGENTS.md`、設計ドキュメント、タスク一覧、リポジトリ規約を尊重する。
- ファイル編集は `plan.md` と必要な `spec/` 配下に限定する。
- 出力は日本語で記述する。
- 承認済みで次フェーズへ進める場合は、その旨を最終報告に明記する。
- ただし、次フェーズへの移行はメインエージェントが行い、成果物作成・更新は次フェーズのサブエージェントに委譲する。
- 未承認または `Open` の確認事項がある場合は、次フェーズへ進める案内をしない。

## 完了条件

### 質問待ちドラフト完了条件

- `spec/{yyyymmdd_feature}/plan.md` が存在する。
- 入力要件または `design.md` から計画の根拠が記載されている。
- HOW の未決事項が `確認事項` と `質問ラウンド` に記載されている。
- 質問ラウンド、回答欄、特記事項・補足欄、ラウンド判定が記載されている。
- 清書対象セクションを省略するか、「質問回答後に清書」と明記したプレースホルダーだけにしている。
- `次に取るべきステップ` が「ユーザーが HOW 質問に回答する」になっている。
- 承認を促していない。
- ユーザーの明示承認前は `承認状態: Pending` になっている。

### レビュー待ちドラフト完了条件

- `spec/{yyyymmdd_feature}/plan.md` が存在する。
- 入力要件または `design.md` から計画の根拠が記載されている。
- HOW の確認事項が `Resolved` になっている。
- タスク分解、対象ファイル、依存関係、検証方法が明文化されている。
- 実行サマリ、追加・修正・削除で区分した変更ファイル一覧、変更ファイル詳細、詳細手順が記載されている。
- 変更種別に応じて、公開名、input/output、エラー時の扱い、
  既存コードとの接続箇所が明記されている。
  該当しない場合は理由つきで `該当なし` になっている。
- 各タスクの完了条件が明記されている。
- `実装引き継ぎチェック` がすべて `OK` または根拠つきの `該当なし` になっている。
- `次に取るべきステップ` が明記されている。
- 実装方針が `Confirmed` の根拠だけで構成されている。
- `Docs-derived` / `Assumption` / `Open` が実行サマリ、変更ファイル一覧、変更ファイル詳細、タスク分解、詳細手順、実装引き継ぎチェックに混入していない。
- ユーザーの明示承認前は `承認状態: Pending` になっている。

### 承認完了条件

- ユーザーが会話上で明示的に内容を承認している。
- 不明点への質問とユーザーフィードバックが反映されている。
- `承認状態` が `Approved` になっている。
